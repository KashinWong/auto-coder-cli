# Feature Specification: 澄清前项目预判 — 多角色并行 Fan-out

**Feature Branch**: `001-clarify-fanout-roles`
**Created**: 2026-06-10
**Status**: Draft
**Input**: 把澄清卡发出前的「项目预判」从单次单角色，升级为编排层并行的多角色（产品经理 / 架构师 / 测试工程师）fan-out，再综合成单个预判结果。

## 背景与问题 (Context)

auto-coder-cli 在向用户发出「需求澄清卡」之前，会先让引擎读一遍目标项目代码，对需求做一次结构化预判（涉及模块、技术风险、范围边界、验收建议、是否已可立项、本轮该问哪些问题）。当前这一步是**单次、单视角**的：一个 prompt 让引擎「浏览代码 + 输出一段 JSON」。

单视角预判对复杂/大型项目容易看得不够全：偏产品的范围边界、偏架构的集成点风险、偏测试的边界用例，往往在一次泛泛浏览里被平均化、被遗漏，导致澄清卡问得不到点子上，或漏掉关键缺口，后续返工。

## 目标 (Goal)

让预判在发卡前更"懂"项目：用多个固定关注点的角色各自独立审视同一需求与同一份代码，再把多视角结论收敛成**一张**澄清卡所需的单一预判，从而提高澄清卡的针对性、减少澄清轮次和返工。

## 非目标 (Non-Goals)

- 不改澄清卡的展示形态、字段结构或交互（`Prediction` 数据结构对外保持兼容）。
- 不改澄清状态机轮次逻辑（`ready_to_charter`、`_MAX_ROUNDS`、progress 编解码）。
- 不引入新的外部依赖或新的引擎类型；仍只用现有引擎（`claude --print`）。
- 不替目标项目跑真正的测试/构建；角色只做"读代码 + 分析"。

## User Scenarios & Testing *(mandatory)*

### 主要用户 (Actors)

- **需求提交者**：在飞书提交需求、收到并填写澄清卡的人。其体验由澄清卡质量决定。
- **流水线运维者**：配置 `config.yaml`、关注预判成本与时延的人。

### Primary User Story

作为需求提交者，当我提交一个落在「已开启多角色预判」项目上的需求时，系统在发澄清卡前会从产品、架构、测试三个视角分别审视我的需求与项目代码，使我收到的澄清卡：涉及模块更准、风险点更全、问题更切中关键缺口——从而我能一轮把信息补齐，更快进入立项。

### User Stories（优先级与 Scenario 锚点）

- **US1 (P1) — 多角色并行预判 + 综合**：开启项目并行多视角审视并合成单个 Prediction（含多轮 prior_qa 透传）。覆盖 Scenario 1、5。
- **US2 (P1) — 未开启零回归**：未开启项目行为与现状逐字节一致、零额外引擎调用。覆盖 Scenario 2。
- **US3 (P2) — 三级容错降级**：部分角色挂 / 全挂 / 综合步挂 时澄清不中断。覆盖 Scenario 3、4、6。


### Acceptance Scenarios

1. **Given** 某项目已开启多角色预判，**When** 一个新需求进入澄清，**Then** 系统并行让各配置角色各自读项目产出分析，并合成出一份满足「最多 3 问、能推断的不问、信息足够则 ready=true」约束的预判，再据此渲染澄清卡。
2. **Given** 某项目**未**开启多角色预判，**When** 一个新需求进入澄清，**Then** 系统行为与现状完全一致（单次单角色预判），不产生额外引擎调用。
3. **Given** 多角色预判中某个或多个角色执行失败/超时，**When** 至少一个角色成功返回，**Then** 系统用成功角色的结果完成合成，澄清流程不中断。
4. **Given** 多角色预判中**所有**角色都失败/超时，**When** 合成无输入可用，**Then** 系统降级为空预判（与现有「预判失败降级」语义一致），澄清流程仍继续发卡，绝不阻断。
5. **Given** 第二轮及以后的澄清（已有历轮问答 prior_qa），**When** 触发多角色预判，**Then** 历轮问答同样喂给各角色，已答问题不被重复问出。
6. **Given** 合成步本身失败/超时，**When** 各角色已有输出，**Then** 系统以一个确定性的兜底合并（去重 + 截断至 3 问）产出预判，不因合成失败而丢弃已得到的多视角信息。

### Edge Cases

- 项目未匹配到（`project_path` 为空）：与现状一致，直接返回空预判，不发起任何角色调用。
- 角色配置为空或缺失：回退到现有单次单角色预判。
- 角色之间产出大量重叠问题：合成必须去重并按影响排序，最终不超过 3 问。
- 各角色都判 `ready=true` 但仍各自抛出问题：合成需以「问题是否真阻断实现/验收」为准收敛，倾向 ready。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持按项目级开关启用「多角色并行预判」；未启用的项目维持现有单次单角色预判，且不产生额外引擎调用。
- **FR-002**: 启用时，系统 MUST 让每个已配置角色在目标项目目录下**各自独立**审视同一需求与同一份历轮问答，产出该角色视角的结构化分析。
- **FR-003**: 角色集合 MUST 可在 `config.yaml` 中配置（至少支持产品经理、架构师、测试工程师三类），每个角色含其关注点描述；未配置时回退到单次单角色预判。
- **FR-004**: 多个角色的审视 MUST 并行执行，使整体时延 ≈ 最慢单个角色 + 综合步（而非各角色串行求和）。
- **FR-005**: 系统 MUST 有一个「综合步」把各角色产出收敛为**单个** `Prediction`；综合步 MUST NOT 重新扫描项目代码（只对各角色文本做归并、去重、排序）。
- **FR-006**: 合成出的 `Prediction` MUST 遵守现有约束：`questions` 最多 3 个、能从代码/需求推断的不问、信息足够时 `ready=true` 且 `questions` 为空。
- **FR-007**: 合成出的 `Prediction` MUST 与现有数据结构字段完全兼容（modules / risks / scope_hint / acceptance_hint / ready / ready_reason / questions），下游澄清卡渲染无需改动。
- **FR-008**: 任一角色失败/超时 MUST 不影响其他角色；只要至少一个角色成功，合成 MUST 基于成功结果完成。
- **FR-009**: 所有角色都失败/超时，或综合步无可用输入时，系统 MUST 降级为空预判并继续澄清流程（保持「预判绝不阻断澄清」的现有容错语义）。
- **FR-010**: 综合步自身失败/超时时，系统 MUST 以确定性兜底合并（去重 + 截断至 3 问）产出预判，不丢弃已得到的角色输出。
- **FR-011**: 第二轮起的增量预判 MUST 把历轮问答传递给每个角色，已答问题不被重复问出。
- **FR-012**: 多角色模式 MUST 通过现有的预判注入缝接入，使得「单次 / 多角色」两种实现可整体切换而不改动澄清编排核心逻辑。
- **FR-013**: 文档 MUST 说明多角色模式的成本含义：每轮澄清的引擎调用次数从 1 次变为 N（角色数）+1（综合步）次；并说明并行后时延≈单角色 + 综合步。

### Key Entities

- **角色 (Role)**：一个预判视角的定义。属性：名称、关注点说明。来自配置。
- **角色产出 (Role Finding)**：单个角色对需求的结构化分析（其视角下的 modules / risks / questions / 范围与验收看法）。
- **预判 (Prediction)**：合成后供澄清卡使用的单一结果，字段沿用现状，对下游不可见地由"单次"或"多角色合成"产生。

## Success Criteria *(mandatory)*

- **SC-001**: 对未开启该功能的项目，澄清行为与改造前**逐字节一致**（同样的预判调用次数、同样的卡片内容路径），通过回归测试验证。
- **SC-002**: 角色调用并行生效，可验证：用带延迟的桩引擎，断言开启时各角色被并发派发（墙钟 ≈ max(单角色) + 综合，而非各角色耗时求和）。
- **SC-003**: 在「部分角色失败」「全部角色失败」「综合步失败」三种注入故障下，澄清流程都能继续发卡，不中断、不抛异常到调用方。
- **SC-004**: 合成结果在任意输入组合下都满足"问题 ≤ 3"的硬约束。
- **SC-005**: 该功能的开关、角色配置、降级路径均有自动化测试覆盖，可在不依赖真实引擎的前提下运行（通过注入桩 predict/capture）。

---

## Assumptions

- 角色之间彼此独立、无需互相看到对方产出（真正的 fan-out，而非链式）；跨角色的协调发生在综合步。
- 综合步可由一次"不读项目、只读各角色文本"的引擎调用完成；其失败有确定性兜底，故综合步质量不是可用性的硬依赖。
- 现有 `run_engine_capture` 的"失败/超时返回空串、由调用方降级"契约保持不变，多角色实现复用它。
- 成本放大（N+1 倍引擎调用）对已开启的项目是可接受的，因为开关默认关闭、仅复杂项目按需开启。

## Dependencies

- 现有引擎运行设施 `run_engine_capture`（捕获 stdout、失败返回空串）。
- 现有澄清编排 `ClarifyOrchestrator` 的 `predict_fn` 注入缝。
- `config.yaml` 项目配置（新增角色与开关字段）。
