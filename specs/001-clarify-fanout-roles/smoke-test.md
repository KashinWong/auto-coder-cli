## 1. 关闭路径（默认，零回归）

- **前置**：`config.yaml` 中目标项目**不含** `clarify_fanout`（现状）。
- **操作**：在飞书提交一条命中该项目的需求，触发澄清。
- **预期**：收到澄清卡，内容与改造前一致；后台单次引擎预判（无综合步、无额外调用）。

## 2. 开启路径（多角色并行）

- **前置**：给某项目（建议先用非生产项目，如 `gomoku-h5`）加：
  ```yaml
  gomoku-h5:
    # ...原有配置...
    clarify_fanout:
      enabled: true
  ```
- **操作**：提交一条命中该项目的需求，触发澄清。
- **预期**：
  1. 后台并行起 3 个角色引擎调用（产品经理/架构师/测试）+ 1 个综合调用 = 4 次。
  2. 澄清卡的「涉及模块 / 风险点」比单视角更全，问题更切中关键缺口，且**问题数 ≤ 3**。
  3. 端到端时延 ≈ 最慢单角色 + 综合（而非 4 次串行求和）。
- **验证次轮**：回答部分问题后再次触发（prior_qa 非空），确认已答问题不被重复问。

## 3. 故障演练（降级不阻断）

> 自动化已覆盖；如需手动验证，可临时制造引擎不可用。

- **部分角色挂**：让某角色超时（如临时改小该路径超时 / 断代理瞬时）→ 澄清卡仍发出，用存活角色结果。
- **全部角色挂**：引擎完全不可用 → 降级为空预判，澄清卡仍发出（只是无预判摘要）。
- **综合步挂**：角色成功但综合超时 → 走确定性兜底合并，卡片仍含合并后的模块/风险/≤3 问。

## 4. 回滚

删除该项目的 `clarify_fanout` 段（或设 `enabled: false`），行为立即回到单次单角色预判，无需改代码、无需重启逻辑变更。
